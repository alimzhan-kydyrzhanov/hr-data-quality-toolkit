## 2. Теория с нуля

### 2.1 Employee master data (HR master data)
Это «паспорт» сотрудника в HR-системе: ID, имя, email, дата найма/увольнения, страна, cost center, должность, FTE, руководитель. Из этих данных потом считаются зарплата (payroll), доступы, отчёты, оргструктура.
**Аналогия:** как карточка пациента в клинике Ala — если там ошибка в дате или процедуре, ошибётся всё, что дальше. В SAP это хранится в SAP SuccessFactors Employee Central / SAP HCM (я с ними не работал, но понимаю, какие данные там лежат и почему их точность критична).

### 2.2 Ключевые HR-термины
- **FTE (Full-Time Equivalent)** — доля ставки: 1.0 = полная, 0.5 = половина. Больше 1 или 0 — ошибка.
- **Cost center** — «кошелёк» подразделения, куда списываются расходы на сотрудника.
- **Hire / termination date** — дата найма / увольнения. Увольнение раньше найма — логически невозможно.
- **Manager ID** — ссылка на другого сотрудника. Если такого ID нет — «битая ссылка» (как foreign key в БД).
- **P&C = People & Culture** — так в SAP называется HR.

### 2.3 Data quality — измерения
- **Completeness** (полнота): обязательные поля заполнены → `check_mandatory`.
- **Validity** (корректность формата): email, FTE в диапазоне → `check_email_format`, `check_fte`.
- **Uniqueness** (уникальность): нет дублей ID → `check_duplicate_ids`.
- **Consistency** (согласованность): поля не противоречат друг другу → currency vs country, termination vs hire.
- **Referential integrity**: manager существует → `check_manager_exists`.
**Аналогия:** как ты проверял записи в клинике «до и после сохранения» — тут то же, только автоматически и для всех записей сразу.

### 2.4 Excel для анализа данных
- **Excel Table** (Ctrl+T) — диапазон с именем, фильтрами и автоматическим расширением.
- **Conditional formatting** — раскраска по правилу (high = красный).
- **COUNTIF / COUNTIFS** — посчитать строки по условию. **XLOOKUP / VLOOKUP** — найти значение по ключу (как JOIN в SQL).
- **PivotTable** — сводная таблица: группировка и подсчёт мышкой (как GROUP BY).
- **Формулы vs значения**: в Summary лежат живые формулы — если HR-коллега удалит исправленную строку из Issues, цифры пересчитаются сами.

### 2.5 openpyxl
Python-библиотека, которая пишет настоящий .xlsx (формулы, стили, таблицы, графики). Pandas хорош для расчётов, openpyxl — для «красивого» файла, который откроют люди.

### 2.6 AI agent и agentic AI
Обычный LLM-вызов: вопрос → ответ. **Агент**: модель сама решает, какой инструмент вызвать (`get_employee`, `find_managers`), получает результат, думает дальше — цикл до ответа.
**Аналогия:** стажёр, которому дали доступ к справочникам: он сам смотрит карточку сотрудника и список cost centers, а потом пишет предложение руководителю. Но **сам ничего не меняет** — это **human-in-the-loop**.
- **Tool use** — модели передаётся JSON-схема инструментов; она отвечает `stop_reason="tool_use"` и аргументами.
- **Output validation** — ответ модели проверяется кодом (`validate`): поле из разрешённого списка, confidence 0–1. Иначе — fallback на правила.
- **MAX_STEPS** — защита от бесконечного цикла.

### 2.7 Тесты, Docker, CI
- **pytest** — автоматические проверки. FakeClient имитирует Claude, чтобы тесты шли без интернета и денег.
- **Docker** — «коробка» с Python и зависимостями, запускается одинаково везде.
- **GitHub Actions CI** — при каждом push запускает тесты и прикладывает Excel-отчёт как artifact.

## 4. Каждый файл: что и ЗАЧЕМ

- **`hr_dq/generate_data.py`** — генерирует 200 сотрудников × 6 месяцев, вставляет 11 типов ошибок, доля ошибок падает со временем. *Зачем:* реальные HR-данные — персональные (GDPR), их нельзя брать; падающий тренд нужен, чтобы показать отчёт по трендам.
- **`hr_dq/checks.py`** — 11 функций-правил, каждая возвращает список issues с severity и понятным сообщением. `safe_autofix` чинит только то, что не меняет смысл (пробелы, регистр), и пишет audit log. *Зачем:* разделение «найти» и «исправить» — в HR нельзя молча менять данные; каждое изменение должно быть прослеживаемо.
- **`hr_dq/agent.py`** — инструменты, цикл агента, валидация, fallback. *Зачем:* AI ускоряет разбор ошибок, но не должен быть единственной точкой отказа и не должен писать в систему без человека.
- **`hr_dq/excel_report.py`** — 6 листов, формулы, Excel Table, conditional formatting, график. *Зачем:* HR-коллеги работают в Excel, а не в Python.
- **`hr_dq/main.py`** — запуск всего процесса одной командой + тренды по месяцам.
- **`tests/test_checks.py`** — каждое правило ловит свою ошибку; чистая запись = 0 issues; autofix не трогает смысловые поля.
- **`tests/test_agent_and_report.py`** — fallback без ключа, агент с FakeClient, невалидный ответ LLM → правила, структура Excel.
- **`Dockerfile`, `.github/workflows/ci.yml`** — воспроизводимый запуск и автотесты.

## 5. Решения и компромиссы

| Решение | Почему | Цена / альтернатива |
|---|---|---|
| Агент только предлагает, не исправляет | Ошибка в HR-данных = ошибка в зарплате/доступах; нужна ответственность человека | Медленнее, чем авто-исправление |
| Rule-based fallback | Работает без API-ключа, детерминированно, бесплатно | Правила умеют меньше, чем LLM |
| Autofix только для пробелов/регистра | Эти изменения не меняют смысл | Остальное чинится вручную |
| Формулы в Summary, а не числа | Пересчитываются, если коллега правит файл | openpyxl не считает формулы сам (считает Excel при открытии) |
| Excel, а не дашборд | Команда работает в Excel, ноль внедрения | Нет real-time обновления |
| Synthetic data | GDPR, нельзя реальные персональные данные | Распределение ошибок условное |
| Лимит 30 issues для агента | Стоимость и время API | Остальные — только правила |

## 9. Вероятные вопросы и ответы

1. **Расскажите о проекте.** — Инструмент для проверки качества employee data: 11 правил, Excel-отчёт для HR с трендами и AI-агент, который предлагает исправления на подтверждение человеку.
2. **Почему synthetic data?** — Employee data — персональные данные, GDPR; для демо нельзя использовать реальные.
3. **Какие проверки самые важные?** — High severity: пустые обязательные поля, дубли ID, увольнение раньше найма, возраст при найме — они ломают payroll и отчётность.
4. **Как вы определяете data quality score?** — Доля сотрудников без единой ошибки: 1 − affected / total.
5. **Почему агент не исправляет сам?** — Ошибка в HR-данных влияет на зарплату и доступы; нужен человек и audit trail. Агент ускоряет анализ, решение — за человеком.
6. **Что если LLM ответит ерундой?** — Ответ валидируется кодом; невалидный → rule-based fallback. Это покрыто тестом.
7. **Что такое agentic AI в вашем проекте?** — Модель в цикле сама выбирает инструменты (карточка сотрудника, справочники, поиск руководителей), получает результаты и формирует предложение.
8. **Какие функции Excel вы знаете?** — COUNTIF/COUNTIFS, SUMIFS, XLOOKUP/VLOOKUP, IF, PivotTable, conditional formatting, Excel Tables, фильтры, freeze panes, графики.
9. **Чем VLOOKUP отличается от XLOOKUP?** — XLOOKUP ищет в любую сторону, по умолчанию точное совпадение, не ломается при вставке колонок.
10. **Как бы вы нашли дубли в Excel?** — Conditional formatting → Duplicate values, или `COUNTIF(A:A,A2)>1`, или Remove Duplicates (но сначала проверить, какую запись оставить).
11. **Вы работали с SAP HR?** — Нет. Но в клинике и отеле я вёл записи пациентов и гостей, проверял точность и полноту, передавал регистрационные данные в полицию — тот же принцип ответственности за данные. SAP-системам готов учиться.
12. **Как вы обеспечиваете точность при ручном вводе?** — Проверка до и после сохранения, сверка с источником, чек-листы; в проекте — автоматические правила.
13. **Как вы бы улучшили процесс?** — Вынести правила в конфиг, хранить статусы issues в БД, еженедельный отчёт трендов для команды, автоисправление только безопасных случаев с audit log.
14. **Как объяснить ошибку коллеге, не технарю?** — Колонка message: «Termination date is before hire date» + что нужно подтвердить и у кого.
15. **Что такое FTE и cost center?** — См. 2.2.
16. **Почему формулы, а не числа в Summary?** — Пересчитываются при правках в файле.
17. **Как тестируете AI-часть без API?** — FakeClient имитирует ответы модели: tool_use, затем JSON.
18. **Что делает Docker / CI?** — Одинаковый запуск везде; тесты и Excel-отчёт на каждый push.
19. **Самое слабое место проекта?** — Данные синтетические и правила в коде; см. раздел 7.
20. **Как используете AI в обычной работе?** — Claude Code / Cursor для прототипов и рутины, всегда с проверкой результата.
